E-Commerce Project — Database Schema

A schema sized for what you're building toward (Spring Security → JPA → Cart/Orders → Payments → Reviews), not just what you need today. Add tables in the phases below as you reach that topic — don't build it all on day one.

Phase 1 — Auth (Spring Security, now)

users

Column Type Notes
id BIGINT, PK, auto-increment
username VARCHAR(50), UNIQUE, NOT NULL
email VARCHAR(100), UNIQUE, NOT NULL
password VARCHAR(255), NOT NULL store BCrypt hash, never plaintext
enabled BOOLEAN, DEFAULT true for account activation/deactivation
created_at TIMESTAMP, DEFAULT now()
updated_at TIMESTAMP

roles

Column Type Notes
id BIGINT, PK
name VARCHAR(30), UNIQUE e.g. ROLE_ADMIN, ROLE_CUSTOMER

user_roles (join table — many-to-many)

Column Type Notes
user_id BIGINT, FK → users.id
role_id BIGINT, FK → roles.id composite PK (user_id, role_id)

Why split roles out instead of a role column on users: a user can hold multiple roles, and it's the standard shape Spring Security's UserDetailsService expects — you'll wire this straight into GrantedAuthority.

Phase 2 — Catalog (once you touch JPA/relationships)

categories

Column Type Notes
id BIGINT, PK
name VARCHAR(100), NOT NULL
description VARCHAR(500)
parent_category_id BIGINT, FK → categories.id, NULLABLE self-reference, for subcategories (e.g. Electronics → Laptops)

products (extend your existing table)

Column Type Notes
id BIGINT, PK already have this
name VARCHAR(150), NOT NULL
description TEXT
price DECIMAL(10,2), NOT NULL never use FLOAT/DOUBLE for money
stock_quantity INT, NOT NULL, DEFAULT 0
sku VARCHAR(50), UNIQUE stock-keeping unit
category_id BIGINT, FK → categories.id
active BOOLEAN, DEFAULT true soft-disable instead of hard delete
created_at TIMESTAMP
updated_at TIMESTAMP

product_images

Column Type Notes
id BIGINT, PK
product_id BIGINT, FK → products.id
image_url VARCHAR(500)
is_primary BOOLEAN, DEFAULT false

Phase 3 — Addresses & Cart

addresses

Column Type Notes
id BIGINT, PK
user_id BIGINT, FK → users.id
line1, line2 VARCHAR(200)
city, state, country VARCHAR(100)
postal_code VARCHAR(20)
type VARCHAR(20) SHIPPING / BILLING
is_default BOOLEAN

carts

Column Type Notes
id BIGINT, PK
user_id BIGINT, FK → users.id, UNIQUE one active cart per user
created_at TIMESTAMP

cart_items

Column Type Notes
id BIGINT, PK
cart_id BIGINT, FK → carts.id
product_id BIGINT, FK → products.id
quantity INT, NOT NULL
UNIQUE(cart_id, product_id) prevents duplicate rows for the same product

Phase 4 — Orders & Payments

orders

Column Type Notes
id BIGINT, PK
user_id BIGINT, FK → users.id
shipping_address_id BIGINT, FK → addresses.id
billing_address_id BIGINT, FK → addresses.id
status VARCHAR(20) PENDING, CONFIRMED, SHIPPED, DELIVERED, CANCELLED
total_amount DECIMAL(10,2)
order_date TIMESTAMP

order_items

Column Type Notes
id BIGINT, PK
order_id BIGINT, FK → orders.id
product_id BIGINT, FK → products.id
quantity INT
price_at_purchase DECIMAL(10,2) snapshot the price here — don't join live to products.price, since price changes later shouldn't rewrite history

payments

Column Type Notes
id BIGINT, PK
order_id BIGINT, FK → orders.id, UNIQUE
method VARCHAR(30) CARD, UPI, COD
status VARCHAR(20) PENDING, SUCCESS, FAILED, REFUNDED
transaction_id VARCHAR(100) from a mock/real payment gateway
amount DECIMAL(10,2)
paid_at TIMESTAMP

Phase 5 — Engagement (polish, later)

reviews

| id, product_id (FK), user_id (FK), rating (1–5, INT), comment (TEXT), created_at |

wishlists + wishlist_items

Same shape as cart/cart_items, just without quantity.

coupons

| id, code (UNIQUE), discount_percent, valid_from, valid_to, usage_limit, times_used |

Design notes worth carrying forward

  • Every table gets created_at/updated_at. Cheap now, invaluable later for debugging and for demoing "audit trail" awareness in interviews.
  • Soft delete over hard delete for products and users (active/enabled flags) — real e-commerce systems rarely hard-delete rows that other tables reference.
  • Money is always DECIMAL, never FLOAT/DOUBLE. This is a classic interview gotcha.
  • Snapshot data at transaction time (order_items.price_at_purchase) rather than always joining live — a recurring real-world pattern once you build orders.
  • Index foreign keys (product_id, user_id, order_id everywhere) once the data grows past toy size — good to mention even now.
  • Map tables to Java concepts as you go: users/roles → Spring Security; categories self-reference → JPA @ManyToOne on itself; cart_items/order_items → @OneToMany; payments → a natural place to later plug in a Strategy pattern per payment method.

Suggested build order

  1. users, roles, user_roles — Spring Security
  2. categories, extend products, product_images — first JPA relationships
  3. addresses, carts, cart_items — more relationships, DTOs
  4. orders, order_items, payments — transactions, @Transactional
  5. reviews, wishlists, coupons — polish for the portfolio version
